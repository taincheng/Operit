# 02 客户端：三个包各自解析平台真实 id

[DONE]

三个包都改在同一处：取到分享链接之后、写记录之前，用 `Tools.Net.http` GET 一次短链
（实测会自动跟随 302），从跳转后的页面里解析稳定 id；解析失败抛错，不写这条记录。

| 包 | 版本 | 解析规则 | 本地去重 |
| --- | --- | --- | --- |
| 抖音 | 0.4.0 → **0.5.0** | `rel="canonical"` 里的 `/video/(\d+)` | `recordIndexByAwemeId` → `recordIndexByContentId` |
| 快手 | 0.2.0 → **0.3.0** | `"photoId"\s*:\s*"([A-Za-z0-9_-]+)"` | `storedVideoIds`（短码）→ `storedContentIds` |
| 小红书 | 0.2.0 → **0.3.0** | `"noteId"\s*:\s*"([0-9a-fA-F]{16,32})"` | `storedItemIds`（短码）→ `storedContentIds` |

每个包都删掉了原来那个「从 url 里抠短码当标识」的函数（抖音 `videoIdOf`、快手 `videoIdOf`、
小红书 `itemIdOf`），没有留兼容分支：新记录一律带 `content_id`，旧记录（没有这个字段）
不参与去重，也不会被硬猜着合并。

## 记录结构

三个包的记录都新增 `content_id: string`。抖音的记录里，`aweme_id` 这个字段名一并改名，
历史记录里的旧字段名不再被读取（那是没发布过的中间态）。

## 单条工具

`*_collect_share_link` 的返回值也带上 `contentId`，与批量采集用同一套解析，避免两处逻辑漂移。

## 失败语义

解析失败 → 抛错 → 本片中断。选这个而不是「跳过这一条」：身份错了会安静地污染数据，
要过很久才看得出来；中断则立刻可见，代价只是这一片重跑。

## 设备上的中间态数据

0.4.0 只在**本机调试设备**上装过（没有发布），它写下的 11 行用的是 `aweme_id` 字段名。
改名后这些行读不出来，等于「没有身份」，于是把设备上的抖音 `records.jsonl` 规整了一次
（11 行改名 + 合并 6 组同内容重复行），详见 [03_verification.md](03_verification.md)。
生产与其它设备没有这种行：0.4.0 从未发布。
