# 三个采集包统一内容身份 content_id（2026-10-19）

## 起因

抖音那轮修复（[../douyin_video_counts_20261019/](../douyin_video_counts_20261019/)）发现：**短链码不能当内容身份**，
抖音每次分享都给新短码。用户随后要求「再处理快手收集和小红书收集的工作流」。

## 先诊断，再动手（实测三种情况都不一样）

| 包 | 记录总数 | 不同 (作者, 标题) | 重复行 | 结论 |
| --- | --- | --- | --- | --- |
| 抖音（已修） | 470 | 98 | 372（79%）| 短码每次都变 |
| 快手 | 562 | 153 | 409（72%）| 短码每次都变 |
| 小红书 | 321 | 320 | 1（0%）| 短码**稳定**，那 1 条是同秒重复写 |

各平台的稳定身份（真实分享链接打出来的，取证见 [evidence_shortlink_identity.md](evidence_shortlink_identity.md)）：

| 平台 | 稳定身份 | 证据 |
| --- | --- | --- |
| 抖音 | canonical 里的 `/video/7672977497508440818` | 5 个短码都跳到它 |
| 快手 | 分享页 JSON `"photoId":"5238531002599057662"` | 3 个短码（KlSb2UEZ / JW1dhvtt / 7IFbHrYb）页面里都是它 |
| 小红书 | 分享页 JSON `"noteId":"6a263ade0000000022024db0"` | 短链跳转后的地址就是 `/discovery/item/<noteId>` |

## 征求过的两个决定

1. **v1.2.0 是否已发布**：用户确认「只在本地跑过，没上生产」→ 于是把
   `aweme_id` 彻底改名成平台中立的 `content_id`，旧名与旧列**一行代码都不留**（不是加兼容列）。
   v1.2.0 中间态在本地库里留下的列与索引，用一段一次性 SQL 清掉（写进 hotgo 的部署文档）。
2. **小红书要不要一起改**：用户选「三个平台统一用 content_id」。
   小红书的短码本来稳定，但 v1.3.0 的服务端只按 `(source, content_id)` 判重，
   它若继续不发身份，同笔记就永远不会合并 —— 所以一起改。

## 不做的事

- **不拿短码当兜底身份**。三个包解析失败一律抛错、不写记录：退回去就是把重复行继续写进库。
- **不自动回填历史行**。0.3.0/0.5.0 之前写下的记录没有 `content_id`，它们不参与去重，
  历史行原样留着；重复行的合并是数据决策（挑哪一行、删哪些行），交给人工。
- **不动 v1.1.0 的 `(source, video_id)` 唯一索引**。它挡的是短链层面的重复，
  留着不影响新逻辑（新记录短码每次都不同，不会撞它）。
