# 无人值守与分片续跑

## 旧状态

- 脚本硬超时 30 分钟，见 `app/src/main/java/com/ai/assistance/operit/core/tools/javascript/JsTimeoutConfig.kt`，并且没有协作式检查点，被杀时脚本没有保存机会
- QuickJS 单线程，脚本串行
- `WorkflowScheduler` 支持固定间隔、指定时间与 cron，间隔下限 15 分钟，见 `app/src/main/java/com/ai/assistance/operit/core/workflow/WorkflowScheduler.kt`
- 工作流执行节点可以调用任意工具或内联 jsCode，但没有循环节点
- 外部 adb 广播触发在本机被 HyperOS 拦截，`ScriptExecutionReceiver` 收不到广播，详见 [index.md](index.md) 的实测基线

## 意图

分片与续跑：

- 采集运行时按条数上限与时间上限切分，任一到顶就结束当前片
- 每片结束在插件配置目录写 `progress.json`，记录已处理到的位置、已采集条数与该轮的幂等键前缀
- 下一片从断点继续，不重复采集已完成的部分
- 分片阈值留出安全边际，单片目标不超过 20 分钟，避免贴近 30 分钟硬上限

触发：

- 循环放在脚本内，工作流只负责定时点火，可以给执行节点配置调用采集入口
- 进度用 `sendIntermediateResult` 上报，便于在界面上看到进展
- 不依赖外部 adb 触发

环境前提，需在文档中明确告知使用者：

- 长任务期间要保持应用在前台或处于保活状态，并保持屏幕常亮。仓库目前没有任何锁屏与息屏下的注入处理
- 息屏与锁屏下的可操作性没有代码保障，不要假设可以后台无人值守跑通
- **采集期间不要打开应用，也不要动手机**。两条实测过的坑：冷启动会立刻多点一次火，而新的点火会取消正在跑的那一片（日志 `工作流执行已取消`），那一片已有的记录会保留但上报节点不会执行；人手动搜索或滑动会把页面抢走，让正在跑的那一步直接超时失败。间隔因此要明显大于单片耗时

## 实现

参数：

| 参数 | 含义 |
| --- | --- |
| `keyword` | 搜索关键词 |
| `count` | 本片最多采集多少条，默认 1 |
| `chunk_minutes` | 本片时间上限，默认 18，超过 20 直接报错，避免贴近 30 分钟硬超时 |

进度文件 `progress.json` 落在插件配置目录，字段为 `keyword`、`round_id`、`chunk_index`、`collected_total`、`last_url`、`last_video_id`、`last_stop_reason`、`last_chunk_started_at`、`last_chunk_finished_at`、`updated_at`。

续跑方式与最初的设想有两处不同，都是实测逼出来的：

- 断点记录的是进度与轮次，不是列表位置。搜索结果首屏会浮动，按位置续跑不可靠；可靠的做法是照旧从头进列表，靠 records.jsonl 里的视频标识去重，命中已采集的直接跳过
- 没有「幂等键前缀」。幂等键是每条随机生成的 UUID，分片归属靠 `round_id` 标识。同一个关键词的上一轮没结束就续同一轮，换关键词才开新一轮

界面进展用 `sendIntermediateResult` 上报，每采到一条报一次本片与本轮累计条数。

### 读页面偶发失败的处理

宿主读无障碍树时三次重试只隔约 300ms，页面动画或 provider 繁忙时会连续超时。实测踩到两次，处理方式统一为「在等待语义下把读失败当作还没就绪」：

- `waitForNode` 与 `ensureDouyinForeground` 都容错，超时信息里带上最后一次失败原因，不掩盖真实故障
- 连续读失败时退避，间隔从 500ms 起按次数翻倍、上限 3 秒。之前每 500ms 硬打一次，只会让 provider 一直缓不过来，实测出现过「页面已经加载好、但 10 秒内每次读都失败」的情况
- 搜索结果页的等待上限单独放宽到 30 秒。抖音搜索页要加载封面并自动播放，10 秒不够

### 工作流模板

模板里放两个触发节点：定时触发（15 分钟）用于无人值守，手动触发用于随时试跑。宿主的手动触发只认 `manual` 类型的触发节点，只放定时触发的话，编辑器里的「触发工作流」会直接空跑并记一条失败：`没有手动触发类型的触发节点`。

工具名要用带类型前缀的全名，`douyin_collector:douyin_collect_share_links`。工作流把参数按字符串传，数值参数依然能被正确转换，实测没问题。

另外，包被导入时会**立刻按定时配置点火一次**，不是等满一个周期。

另外，包详情页的自检对话框会把**所有声明过的参数**一起提交，空的数值参数会变成空字符串并被宿主严格转换拒绝。所以手工在对话框里跑这个工具时，`count` 与 `chunk_minutes` 都必须填值；工作流与模型调用只提交自己声明的参数，不受这条影响。

## 验证

分片与续跑已在真机验证。为了让验证可复现且不占半小时，用「把时间上限调小」的方式逼出时间分片，走的是与 18 分钟上限完全相同的代码分支。

| 验证项 | 实测 |
| --- | --- |
| 时间到即收尾，不触及硬超时 | 设时间上限 0.8 分钟，日志 `本片时间上限 0.8 分钟到，结束本片，本片已采 1 条`，`last_stop_reason` 为 `time` |
| 断点文件写入正确 | `progress.json` 记录 `chunk_index=1`、`collected_total=1`、`last_url`、`last_video_id`、两个时间戳 |
| 下一片续上一轮 | 第二次运行日志 `续上一轮：关键词=food 第 1 片已完成，累计 1 条`，`round_id` 与上一片相同，`chunk_index=2`、`collected_total=2` |
| 续跑不重采 | records.jsonl 由 7 条增至 8 条，8 条 URL 全部唯一 |
| 工作流模板注册 | 包详情页显示资源数 1、工作流模板数 1，模板名与描述正确 |
| 工作流模板导入 | 从「工作流 → 从模板新建」导入成功，生成的工作流含定时触发、手动触发、采集、上报四个节点，参数与资源文件一致 |
| 工作流手动触发整链闭环 | 编辑器里「触发工作流」→ 采集节点采满 6 条并返回 `stopReason=count, chunkIndex=5, collectedTotal=6` → 上报节点返回 `batches=1, sent=14, failed=0, pending=0` → 日志 `工作流执行完成`，服务端同批入库 |

导入这条路径上有两个坑，实测踩到，已写进包 README：

- 外部包装好后**不会自动启用**，宿主只对内置包应用清单里的 `enabled_by_default`。包没启用时它的工具仍能在包详情里手动跑，但工作流的模板选择器会把它过滤掉。要在包管理里把该包的开关打开
- 内置模板占了模板选择器的前九条，插件模板分区在**列表最下面**，不滚到底看不到

未覆盖，实现方式已定但没有实测：

- 25 分钟量级的真实长片。本次用 0.8 分钟的上限验证了同一条时间分支，没有真跑满 18 分钟
- 工作流的定时器实际点火。定时触发节点在包导入时与应用重启时都实际跑过，但没有观察到「间隔到点」这一次自然触发
- 中途失败时 `progress.json` 停在最后一个完整条目。进度是每采集一条就写一次，所以失败只会丢掉当前正在处理的那条，这一点来自实现而不是实测
