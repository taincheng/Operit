# 搜索结果集边界与遍历方式

## 现象

关键词 `朗诵` 的这一轮采集里，id 24 到 73 是正常内容（朗诵、诵读、读诗、表达训练），从 id 74 起连续 20 条全是瑞幸咖啡广告，而记录的 `keyword` 字段仍然是 `朗诵`。那 20 条已从服务端删除，并在本地文档记录。

数据侧的分界非常干净：

| 段 | 条数 | 含瑞幸/咖啡/拿铁 | 标题含"朗诵" |
| --- | --- | --- | --- |
| id 24 到 73 | 50 | 0 | 25 |
| id 74 到 93 | 20 | 19 | 0 |

`food` 与 `美食` 两轮的记录零广告，因为那两轮没跑到结果集尽头。

## 原因

不是反爬。反爬会表现为验证页、空信息流、重复同一条或取不到分享链接，而实际拿到的每一条都是正常视频页与正常分享文案（短链、乱码后缀齐全）。

真正的原因写在 driver 的假设里：**详情页里向上滑，滑到搜索结果尽头之后会接到推荐流**。驱动把"下一条"一律当成下一条搜索结果，于是推荐流里的广告也被收了下来，还贴上了搜索关键词的标签。这个标签是客户端自己打的，所以它必然撒谎。

## 探针实测

用一次性探针工具（`douyin_probe_search_list`、`douyin_probe_page`）在真机上取证。探针通过环境变量开关由定时工作流触发，全程不点界面——人工点击会抢掉自动化正在用的前台，实测把采集带崩过。

| 问题 | 实测结果 |
| --- | --- |
| 视频标签首屏有几张卡 | 2 列网格，4 张有效卡片。角标坐标两列 x≈421 与 x≈956，两行 y≈997 与 y≈1969 |
| 读取时的干扰 | 角标节点里混着退化边界（如 `[0,1557][-447,1610]`）。现有 `isNodeVisible` 已经会剔除，探针统计时也要剔除 |
| 列表下滑是否加载更多 | 会。下滑一次后节点数 486 变 533，角标整体上移并出现新的 |
| 详情页有没有"来自搜索"的标记 | 有「相关搜索」。**但广告页同样有**「相关搜索 · 瑞幸高蛋白莓果酸奶饮团购」，所以"有没有相关搜索"不能作为判据 |
| 从详情返回列表后位置是否保持 | 保持。返回前后角标坐标完全一致 |

结论：**漂移在页面内容上认不出来**，只能靠结构约束——把遍历范围钉在搜索列表里。

顺带确认了一条已有的设计假设：采集必须切到「视频」标签。默认的「综合」标签里卡片没有时长角标，还混着图文与直播。

## 意图

把遍历方式从「一路滑到底」改成「按搜索结果页分页驱动」：

- 每次取搜索结果页上可见的一页卡片（实测 4 张），只对这一页的卡取链
- 页内仍然用滑动切换视频，省掉每条回列表的开销
- 这一页取完回列表，下滑一屏取下一页
- 下滑之后没有新卡片出现，说明搜索结果已用尽，本片结束并把结论写进 `progress.json`

这样每一片都只吃搜索结果集里的内容，推荐流再也不会被当成结果收下来。

## 已知取舍

页内滑动顺序与列表顺序不完全一致时，可能重复采到同一页里的邻近条目，或漏掉一条。重复由 records 的视频标识去重兜住；漏掉的下一次进列表时还会遇到。这个代价比把广告当结果收下来小得多。

## 作用域

- `my-packages/douyin-collector/src/packages/douyin_collector.ts` 的采集遍历段
- `stopReason` 增加 `search_exhausted`
- `progress.json` 记录本轮的结束原因，便于下一片判断
- 探针工具与设置页上的诊断入口在改完并验证后删除

## 验证清单

1. 关键词结果集内正常采集，条数目标仍然生效
2. 到达搜索结果尽头时以 `search_exhausted` 结束，不产生任何推荐流或广告记录
3. 分页驱动下不重复采集已入库的视频
4. 连续两片之间能继续推进，不会卡在首页反复重采

## 验证结果

改完后的第一片（关键词 `朗诵`，目标 20 条）实测：

| 验证项 | 实测 |
| --- | --- |
| 分页驱动生效 | 日志逐页打印 `第 N 页：本页可见 X 张卡片，本片这一页取 Y 条`，依次 4/4/4/4/3/3 张 |
| 页间切换开销 | 上一页最后一条到下一页开始约 6 秒（返回列表 + 下滑 + 重读） |
| 条数目标仍生效 | 第 6 页只取 1 条即停，`stopReason=count`，本轮累计 99 |
| 不重复采集 | `skippedDuplicates=0` |
| 内容不再被污染 | 新增 20 条全部是朗诵、诵读、读诗、表达训练内容，疑似广告 0 条 |
| 链路闭合 | 上报批次 2，`sent=114, failed=0, pending=0` |

未覆盖：

- `search_exhausted` 分支尚未实际走到。本轮是"取满条数"先结束，结果页翻到底的情形要等某一轮把结果吃干净才会出现
- `duplicates` 分支（连续 10 条都命中已采集）尚未实际走到

## 一处行为变更

原先"连续 10 条都采集过"会抛错，让工作流节点记一次失败。分页驱动下重复的含义变了：它是"走过本轮已经采过的位置"，不是异常，所以改成以 `stopReason=duplicates` 优雅结束本片，不再制造假失败。
