# 快手 App 采集

按关键词搜索快手，逐条点进搜索结果的作品、走 App 的「分享 → 复制链接」取出 `v.kuaishou.com` 短链，落盘后上报远端。目标形态与已落地的抖音、小红书采集一致。

## 现状

已有：

- 抖音采集器 `my-packages/douyin-collector`，真机验证可用
- 小红书采集器 `my-packages/xhs-collector`，真机验证可用，见 [小红书采集计划](../xiaohongshu_collector_20261012/index.md)
- 上报契约已定，见 [采集上报服务端接口](../device_automation_platform_20261008/server_api.md) 与 [记录落地与 outbox 上报](../device_automation_platform_20261008/03_record_store_and_outbox.md)。请求体里的 `items[].source` 明确写着「为将来的其他来源留位」
- 上报地址与令牌已中立化为 `COLLECTOR_BASE_URL` / `COLLECTOR_TOKEN` 两个共用键，见 [上报配置键名中立化](../xiaohongshu_collector_20261012/04_shared_upload_config_migration.md)
- 宿主原语齐备：`Tools.UI`（`getPageInfo` / `tap` / `swipe`）、`UINode`、`Tools.System.shell`（走 Shizuku，设备上已装 `moe.shizuku.privileged.api`）、`Tools.Net.http`、`Tools.Files`
  - 2026-10-15 起快手包 0.2.0 已不再使用 `Tools.System.shell`，权限档「无障碍」即可运行；改动与真机回归见 [collector_accessibility_only_20261015](../collector_accessibility_only_20261015/index.md)

缺失：

- 快手没有任何 driver

设备侧：Operit debug 1.12.2、无障碍 provider `com.ai.assistance.operit.provider` 已启用。快手 14.1.10.46550（`com.smile.gifmaker`）。

## 实测基线

以下结论来自 2026-10-14 的真机实测。设备 Xiaomi 24094RAD4C，HyperOS，Android 15（API 35），屏幕 1080×2400、密度 450，App 窗口可用区 y ∈ [104, 2267]，快手 14.1.10.46550。

复现脚本见 [probe_ks.py](probe_ks.py)，它对每一步都打印判定依据，改 driver 前可以先用它核对现场。

### 读取通道

- **快手的搜索页与详情页都能 `uiautomator dump`**，包括视频播放中的详情页。这一点与抖音（搜索页窗口永不 idle、dump 必然失败）相反，探针因此可以用 adb 口径复核每一步
- driver 走无障碍 provider 档（`Tools.UI.getPageInfo`），不走 dump。**provider 会返回无文案、无 content-desc 的节点**，实测凭据是同一台设备上留下的抖音树快照 `/sdcard/Download/Operit/douyin_nodes.json`：里面 30 个节点 `text` 与 `desc` 都为空但 `clickable=true`，其中 11 个是抖音搜索页的 `ActionBar$Tab`（标签行，只有 `className` 与 `bounds`）。快手顶层标签是同类节点，因此可以定位
- provider 的 `className` 是**简名**（`View`、`EditText`、`TextView`），不是全名

### 搜索入口

- deep link `kwai://search?keyword=<urlencoded>` 配合显式包名 `com.smile.gifmaker`，直达 `com.yxcorp.plugin.search.SearchActivity`，搜索框与结果集都按关键词生效。实测关键词 `家装`
- 搜索框文本节点是 `resource-id` 以 `search_result_text` 结尾的 TextView，内容等于关键词。这是搜索结果页就绪的判据
- 试过的其它 deep link 变体（`&tab=2`、`&tab=video`、`kwai://search/video`、`&type=video`）**都不能直接落到视频标签**，全部落在默认的「综合」

### 顶层标签行是自绘的，没有文案

搜索页有两行横向标签：

- 第一行是内容类型：`综合`、`直播`、`视频`、`用户`、`智能`、`商品`、`图集`（可左右滚，最后一个「图集」常被裁掉，所以节点数实测 6 到 7 个不等）。**这 7 个标签是自绘节点**：`class=android.view.View`、`text` 与 `content-desc` 都为空、没有 `resource-id`，只有 `bounds` 与 `clickable=true`。节点树里读不到「视频」两个字，**只能按位置定位**
- 定位规则：`resource-id` 以 `:id/tabs` 结尾的 `HorizontalScrollView` 是标签行容器，它子树里的可点击 `View` 按左边界排序，第 3 个（下标 2）就是「视频」，实测中心点 `(440, 289)`
- 第二行是内容筛选 chip（`全部`、`博主`、`旗舰店`、`广告`、`客厅`、`原木风`…），挂在 `resource-id` 以 `:id/appbar` 结尾的容器下。它只在「综合」下出现；**切到「视频」后这个容器在界面上消失**，所以「视频标签已生效」的判据是「没有可见的 `appbar`，且出现 ≥1 张作品卡片」。注意判据必须带边界有效性，原因见下一节
- 采集固定走「视频」标签。默认的「综合」把咨询广告卡、直播间、用户卡混在一起，直播间与咨询卡都没有分享链接面板

### 无障碍 provider 的树会留下边界退化的节点

这是本次最容易踩错的一条，实测于包内 driver 的排障过程：

- 「综合」页切到「视频」之后，**provider 的树里仍然留着「综合」那一页的节点**：`appbar` 以及它下面所有 chip 都还在，只是 `bounds` 退化成 `[0,352][-1080,491]`、`[0,385][-1996,469]` 这种（`x2 < x1`）。同一时刻 `uiautomator dump` 里根本没有这些节点
- 「视频」的真实卡片 `bounds` 正常（`[11,363][535,1428]`），而「综合」残留的卡片也是退化的（`[0,2277][-1625,2400]`）
- 所以：**所有按 `resource-id` / `content-desc` 取节点的定位器都必须过一遍边界有效性**。少了这一层，切换明明成功也会被判成「没切过去」，采集一直等到超时；或者读到上一条作品的作者、上一条作品的分享按钮。这与抖音回收视图里混进退化节点是同一类现象，抖音那边的 `isNodeVisible` 注释已记录过
- 用 adb 复核时不要只看 provider 的树，两边对同屏节点的取舍不一样

### 分享面板会把「复制链接」推到屏幕外

- 面板高度随作品变化（多一行联系人时更高）。实测到两种屏幕外形态：
  - 整行在屏幕外：目标的可点击容器 `bounds` 是 `[455,2924][624,3227]`
  - **文案节点自己可见、可点击祖先在屏幕外**：祖先 `[455,4336][624,4617]`（还有一次 `[455,2681][624,2984]`），而「复制链接」这四个字落在可见区内
- 所以判据必须落在**真正要被点的那一层**上：先解析出可点击祖先，再看祖先的中心点在不在可视区。查询的是文案节点、点击的是祖先节点，两者 `bounds` 不保证一致；只看文案节点的话，屏幕外的祖先照样会被点一次（点了不生效），随后评论入口超时，这张卡被判成「采不动」白白丢掉
- 处法与抖音一致：按文案定位（不带可见性），祖先不在可视区就把面板内容往上带一点再点，带上限
- 面板项的**顺序**也会随作品变化：「复制链接」有时在第 1 列、有时在第 2 列。按坐标点会点到「作品举报」（实测踩过一次，进了举报页），只能按文案定位


### 结果列表

- 两列瀑布流，卡片高度不齐（实测同屏两张高度差约 150px）
- 卡片节点：`resource-id` 以 `container` 结尾、`clickable=true`、**`content-desc` 形如「朱朱(自装日记)的作品」**，即「作者的作品」。这是卡片身份与定位键，也是本 driver 相比抖音最省事的一点
- 卡片子树里另有 `nick_name`（作者）、`bottom_created_time`（日期）、`feed_card_op_like_tv`（点赞数，或广告卡上的 `广告`）、`tv_video_time`（时长，形如 `01:02`）
- 卡片会被滚动裁切，`bounds` 是**裁切后**的：顶部被标签行挡住时会出现高度只有约 57px 的卡片。裁切后的中心点仍然落在卡片自身范围内，实测按中心点点击仍会打开对应的那条作品
- 起始 y：标签行下沿约 352，卡片从 363 起。App 窗口底 2267，但卡片 `bounds` 会伸到 2400（贴在导航栏下），所以可用性判据用**中心点**而不是 `bounds` 下沿

### 列表位置在往返后是稳定的

这是本 driver 采用「逐卡回列表」的前提，实测两次：

- 进详情 → 立刻返回：五张卡片的 `desc` 与 `bounds` 逐条一致
- 进详情 → **走完整取链流程**（分享 → 复制链接 → 评论框粘贴回读 → 清空 → 返回）→ 返回列表：卡片集合与坐标仍逐条一致，按进入前记下的坐标点第 2 张，打开的正是那一张（`欧派整装大家居`）

因此可以在读页时记下每张卡的中心点，处理完一张回列表再按记下的坐标点下一张，不需要回到列表后重新定位。

### 详情页与分享流程

- Activity：`com.yxcorp.gifshow.detail.PhotoDetailActivity`
- 分享入口：右侧互动条的 `resource-id` 以 `forward_button` 结尾的节点，`content-desc` 形如「分享926」（带计数，用前缀匹配）。点它弹出面板，标题「一键分享至」
- 面板项「复制链接」是 TextView，文本恰为 `复制链接`；它自身 `clickable=false`，可点击祖先是 `resource-id` 以 `share_to_layout` 结尾的 `RelativeLayout`，实测 `[254,1963][423,2267]`，中心 `(338,2115)`。**必须按文案定位**：面板项的顺序会随作品变化，按坐标点会点到「作品举报」（实测踩过一次，进了举报页）
- 点完「复制链接」**面板自动关闭**，不需要返回键，分享计数 +1
- 剪贴板回读：详情页底部的评论入口是 `content-desc` 以 `评论框` 开头的 TextView（实测全文 `评论框发条有爱评论~`）。点开后**评论区在原 Activity 内联展开**（不像小红书会跳 `NoteCommentActivity`），里面是 `resource-id` 以 `editor` 结尾的 EditText
- 粘贴用 `input keyevent 279`；读回 EditText 的 `text`；清空用 `input keycombination 113 29` + `input keyevent 67`；再按一次返回键关闭评论编辑器（焦点仍停在 `PhotoDetailActivity`），第二次返回键才回列表

### 分享文本与短链

实测两例：

```text
https://v.kuaishou.com/KrR1EKUZ 第一次这么直观的感受到软装的重要性！"软装 "快手成长计划 "家居美学 "奶油风 该作品在快手被播放过5.8万次，点击链接，打开【快手】直接观看！
```

```text
https://v.kuaishou.com/KmAuscR9 亲子家庭福音！花了不到4万好看又能装的家，快抄作业！"欧派家居全屋定制 "扩容设计 "好看设计 "家装案例 该作品在快手被播放过24.4万次，点击链接，打开【快手】直接观看！
```

- **短链在最前面**，不像抖音夹在文案中间、小红书在首行末尾。域名是 `v.kuaishou.com`，路径是一段短码，形如 `/KrR1EKUZ`
- **分享文本里没有作者**（抖音是「【作者的作品】」）。所以 `author` 只能从详情页读：`resource-id` 以 `user_name_text_view` 结尾的 TextView，形如 `@朱朱(自装日记)`，去掉前导 `@`
- `title` 取分享文本里短链之后、`该作品在快手` 之前的正文。**不能取详情页的 `element_caption_label`**：那是被截断的（实测尾部带 `… 展开`），而分享文本里是完整正文
- 正文里的话题用 `"` 前缀（`"软装 "快手成长计划`），不是 `#`。原样保留，不做改写
- 分享文本尾句是固定的（`该作品在快手被播放过…次，点击链接，打开【快手】直接观看！`），但播放次数会变，所以只能按 `该作品在快手` 这个前缀切

### 广告作品没有分享入口

- 一部分作品点进去是**广告详情页**：树里出现 `resource-id` 以 `ad_card_container_root` 结尾的节点，右侧互动条整条不在（没有 `forward_button`），底栏只有评论入口
- 实测这类页面在视频网格里**没有可提前识别的外观**：网格里被标了 `广告` 的卡会走到广告页，没被标的卡（`欧派整装大家居`）也会走到广告页。所以只能在详情页判定并跳过
- 判定必须在详情页稳定之后做：正常详情页与广告页的节点结构不同，用 `ad_card_container_root` 直接判，认不出广告页时会等 `forward_button` 超时

### 单条闭环实测

顺序：点卡片 → 等详情页 → 点分享按钮 → 等面板 → 点「复制链接」→ 点评论入口 → 点 EditText → 粘贴 → 读回 → 清空 → 返回 → 返回列表。

adb 探针口径（每步固定 sleep）约 **18 秒/条**，不含详情页加载等待。宿主内用 `Tools.UI` 做条件等待会比探针里的固定等待更快。

## 直接复用的部分

- 分片与续跑的口径：`count` 是本片条数目标，`chunk_minutes` 是本片时间上限（默认 18，上限 20，宿主硬超时 30 分钟），先到者结束，结束原因写进 `progress.json`
- 续跑靠已采记录去重：快手用短链短码
- outbox 状态机与上报契约，只把 `source` 换成 `kuaishou_app`
- 上报地址与令牌：与抖音、小红书共用同一组中立键，不各存一份
- 设置页与工作流模板的形态（含抖音旧键的一次性迁移）
- 失败即抛错并落现场，不做任何兜底；卡片采不动按次跳过、连着 5 张就中断本片；滚动带「是否真的前进」判定

## 已定

- **包保持自包含**，不抽公共 kernel。三个包之间约有 400 行同构代码，抽 kernel 要动到两个已在跑采集的包，代价是两次回归；快手是第三个，但它的 driver 与抖音差异不小，抽出来的公共部分仍然只是记录/outbox/上报那一层，收益不够抵这次回归
- **遍历按「搜索结果卡片」驱动**，不进详情页内滑动。快手的详情页是连续信息流，滑到搜索结果用尽后会接到推荐流，而快手详情页上**没有**可靠的「我还在结果集里」标记（实测 `相关搜索` 模块时有时无，不能当判据）。逐卡点进能保证每一条都来自显式选中的搜索结果卡片
- **广告页整条跳过**，不当作失败，也不占本片的条数目标

## 服务端要跟的一件事

上报契约里的 `source` 目前只接受 `douyin_app` 与 `xiaohongshu_app`，`url` 的域名校验也只放行了 `v.douyin.com`。快手上报的每条会带 `source=kuaishou_app` 与 `v.kuaishou.com` 短链，**服务端需要放行这个来源与域名**。

这一条已实测确认，不是推测：把采到的记录发给当前配置的服务端（`http://localhost:8001`，本机 node 服务，手机侧走 `adb reverse`），响应是

```json
{"accepted":[],"rejected":[{"key":"probe-ks-1","reason":"invalid_url"}]}
```

与 [小红书那次](../xiaohongshu_collector_20261012/index.md#服务端要跟的一件事) 完全同类。客户端按设计不重发 `failed`，服务端放行之后需要把 `outbox.json` 里那几条手工改回 `pending`。

## 验证

遵循仓库约定，本计划不主动运行构建与测试。每一步在真机上的验证方式写在该步骤文档内。

### 落地验证（2026-10-14，真机）

包以 `.toolpkg` 装进 `/sdcard/Android/data/com.ai.assistance.operit.debug/files/packages/`，重启应用后扫描 `errors=0`，在包管理里启用后从 AI 对话调用工具完成端到端验证。

| 项 | 结果 |
| --- | --- |
| 两个关键词各采一片 | `coffee` 3 条、`家装` 3 条，共 6 条记录，短链互不相同 |
| 分片与续跑 | 第二片日志 `续上一轮：关键词=coffee 第 1 片已完成，累计 2 条`，`chunk_index` 递增；换关键词开新一轮 |
| 去重 | 第二片开头补采到的是新短链，已入库的两条被跳过 |
| 广告页跳过 | 家装那片命中 3 个广告详情页（`欧派家居团购`、`漫叶漫剧`），日志 `广告详情页，整条跳过`，`跳过广告页 3 条`，不占条数目标 |
| 分享面板两种版式 | 同片内「复制链接」分别落在第 1 列与第 2 列，按文案定位都点中 |
| 中文关键词 | 由模型产出关键词 `家装`，落盘记录 `keyword` 字段正确 |
| 上报 | `ks_outbox_flush` 发 1 批 3 条，服务端逐条 `rejected`，本地状态置 `failed` 且 `last_error=服务端拒绝：invalid_url` |
| 结束原因 | `progress.json` 的 `last_stop_reason=count` |

排障过程中修掉的三个真实缺陷（前两个都在上面的「实测基线」里单独成节）：provider 树的退化残留节点让「视频标签已生效」永远判假；分享面板把「复制链接」推到屏幕外时直接判成采不动；可见性判据查错了节点（查文案节点、点可点击祖先），祖先在屏幕外时白点一次并丢卡。

### 工作流真机验证（2026-10-14）

模板从「工作流 → 从模板新建 → 插件模板 → 连续采集快手并上报」导入，导入后宿主立刻点火一轮，之后按连续触发续跑。这一节的数据全部来自无人值守的连续多轮，不是单次手工调用。

| 项 | 结果 |
| --- | --- |
| 模板导入 | 列表顶部出现「快手采集与上报」，**默认启用**（另外三条旧采集工作流都是「已禁用」，不会抢界面），5 节点，关键词按模板里的 `家装` 传入 |
| 三个节点顺序 | `ks_outbox_flush`（清积压）→ `ks_collect_share_links`（采一片，目标 3 条 / 上限 5 分钟）→ `ks_outbox_flush`（上报），日志逐条对得上 |
| 单轮产出 | 第 1 片 `新增 3 条，跳过广告页 1 条、采不动的卡片 0 条`，`progress.json` 的 `last_stop_reason=count` |
| 续跑同一轮 | 第 2、3… 片都记 `续上一轮：关键词=家装`，`chunk_index` 递增，`collected_total` 累计（实测连续跑到累计 13 条） |
| 连续触发 | 一轮整轮返回后隔随机 30–120 秒续下一轮（实测第 1 轮结束后约 40 秒起第 2 轮），无人干预连续跑完多轮 |
| 冷启动恢复 | 换包重启应用后，启用中的工作流自动续上（日志 `续上一轮：关键词=家装 第 5 片已完成，累计 10 条` → `本轮第 6 片开始`），不需要手点 |
| 单节点失败不中断链路 | 有一次采集节点因读页面超时抛错，链路仍然走到上报节点并排下一轮，与连续触发计划的「单轮失败也继续排下一轮」一致 |
| 面板上带修复 | 修复后的轮次里日志出现 `「复制链接」的可点击祖先落在可视区外（… y=2832，可视下沿 2250），把面板内容往上带`，随后点中并成功采集，本片 `采不动的卡片 0 条` |

一条测试方法上的注意：跑工作流时**不要用 adb 把 Operit 拉到前台**（`am start` + 点击）。实测这样会把前台从快手抢走，采集节点随后读到的是 Operit 自己的页面并超时——那次失败是测试手法的干扰，不是包或工作流的问题。
